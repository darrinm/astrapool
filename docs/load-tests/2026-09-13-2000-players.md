# Live load test: 2,000 players

Tested `https://astrapool.darrinm.com` on September 13, 2026 UTC with **1,000 independent rooms and 2,000 concurrent WebSocket players**. Two live runs completed, with no protocol errors, lost aim messages, unexpected disconnections, seat changes, or mismatched snapshots.

**Result:** room coordination and recovery worked at this concurrency. Aiming was responsive at 10 updates/second per room. At the maximum-rate aiming workload, the end-to-end test path accumulated a substantial backlog. This is not an unconditional performance pass for 2,000 players at 40 Hz.

## Measurements

The second run separates each phase's latency. All latencies include the load generator, its network connection, Cloudflare, and receipt/validation by the simulated peer. p95 means 95% of measured operations completed within that time.

| Operation | p50 | p95 | p99 |
| --- | ---: | ---: | ---: |
| Create room | 591 ms | 731 ms | 1,171 ms |
| Join/rejoin a player, including seat acknowledgement | 60 ms | 105 ms | 175 ms |
| Aim at 10 Hz per room, before reconnect | 31 ms | 47 ms | 124 ms |
| Aim at 10 Hz per room, after reconnect | 30 ms | 41 ms | 135 ms |
| Aim at target 40 Hz per room | 3,110 ms | 5,320 ms | 5,473 ms |
| Shot broadcast received by both players | 154 ms | 194 ms | 224 ms |
| Result committed and received by both players | 69 ms | 81 ms | 209 ms |

At the high-rate peak, 400,000 previews were submitted over 9.61 seconds (approximately 41,630/second; timer granularity caused a small rate overshoot). All arrived, but delivery including backlog drain took 15.06 seconds (26,556/second). At the end of sending, 154,811 previews remained outstanding. The first, longer peak reached an 8.33-second maximum aim delay.

Normal 10 Hz traffic sustained approximately 9,900 delivered previews/second across the 1,000 rooms, with almost no remaining backlog when sending finished.

## Coverage

- Run 1: 103 seconds, 6,000 shot/result pairs, 900,000 aim previews, 2,000 player reconnects, and 14,000 heartbeat responses.
- Run 2: 76 seconds, 2,000 shot/result pairs, 600,000 aim previews, 2,000 player reconnects, and 6,000 heartbeat responses.
- Both runs reached 2,000 simultaneously open player connections.
- Creation and joining were ramped with 25 rooms in progress at once; the full population joined in about 28–30 seconds.
- Each shot round launched a shot in all 1,000 rooms concurrently and checked both peers' resulting state.
- Every player was disconnected together, then rooms were reconnected with 25 rooms in progress at once. All 2,000 seats and snapshots were restored in about 10 seconds, including the disconnect phase.
- Play and aiming were verified again after reconnecting.
- Every preview carried a room-specific direction and sequence/counter; the receiver checked identity, sequence, delivery, and latency.

## Limits and interpretation

This was a **live backend protocol test from one Node.js process on one computer and network connection**, not a distributed population of browsers. It used protocol-valid synthetic dry-shot results. It did not run browser rendering or physics, download assets for every player, measure geographic latency, or inspect Cloudflare billing.

The peak workload showed sender-side buffering up to 18,406 bytes on an individual socket. The generator used about 1.84 GB RSS, with a 22.76 ms p99 event-loop delay and 118.49 ms maximum delay. These observations do **not** isolate the bottleneck to Cloudflare: the generator, uplink, TLS/socket handling, network path, and service can all contribute. A distributed-generator test is needed before assigning a server capacity ceiling or promising smooth 40 Hz aiming at this concurrency.

Shot latency was measured after the aiming backlog had drained, not while peak aiming and shots competed for bandwidth. This was a short burst test, not a long-duration soak. Starting all 2,000 clients in the same instant was not tested.

The JSON `passed` flag denotes protocol correctness. It does not enforce a latency service-level objective.

All test sockets were closed when each run ended. Only fresh test rooms were used; their data expires through the existing 24-hour room alarm. The local smoke-test runtime was stopped. No production code or settings were changed.

## Reproduce

The reusable harness is `server/room.load.mjs`, also available through `npm run test:load`. Without `--base`, it targets the local Worker on port 8787.

```sh
# Original live workload
npm run test:load -- --base https://astrapool.darrinm.com --rooms 1000 --concurrency 25 --rounds 5 --aim-seconds 5 --peak-seconds 15 --output /tmp/astrapool-load-2000-live.json

# Diagnostic workload, with separate phase latency measurements
npm run test:load -- --base https://astrapool.darrinm.com --rooms 1000 --concurrency 25 --rounds 1 --aim-seconds 10 --peak-seconds 10 --output /tmp/astrapool-load-2000-diagnostic.json
```

Raw results: [original run](2026-09-13-2000-players.json), [diagnostic run](2026-09-13-2000-players-diagnostic.json). Per-phase latency and send/drain timing were added to the harness between these two runs.
